# Phase 6: Booking/Payment Bug Fix Design
**(Read-Only Architecture & Impact Audit)**

## PART 1 — COMPLETE STATUS DEPENDENCY AUDIT
**`Pending`**
- **Created:** `backend/models/bookingModel.js` (`createManualBooking`) sets it as the default.
- **Stored:** `bookings` table (`status` column).
- **Displayed:** Admin panel uses it natively if not `video-sent`. Account dashboard ignores it completely (hidden).

**`Confirmed`**
- **Created:** `backend/models/bookingModel.js` (`markPaid`) sets `status` to `Confirmed`.
- **Stored:** `bookings` table (`status` column).
- **Displayed:** Admin panel natively renders it. Account dashboard ignores it completely (hidden).

**`failed`**
- **Created:** `backend/controllers/paymentController.js` sets it explicitly when Razorpay signature verification fails.
- **Displayed:** Mapped successfully by Account frontend in `pending` tab.

**`video-sent`**
- **Created:** `backend/models/bookingModel.js` (`updateBookingVideo`).
- **Displayed:** Account frontend (`completed` tab) and Admin panel (displays specific status/color/video URL).

**`payment-pending` / `payment-claimed` / `paid`**
- **Read:** `frontend/assets/js/pages/account.js` expects these in `BK_TAB_STATUSES`.
- **Mismatch:** They are *never* generated by the backend or database.

## PART 2 — DATABASE / BOOKING MODEL AUDIT
The `bookings` table includes:
`id`, `devotee_phone`, `puja_id`, `price`, `status`, `payment_status`, `notes`, `created_at`.
- **Unique identifiers:** `id` is a UUID/unique string.
- **Deduplication fields:** None exist. There is no `UNIQUE(devotee_phone, puja_id, status)` constraint.
- **To identify the same session:** `devotee_phone` + `puja_id` (or parsed `notes`) + `status = 'Pending'`.

## PART 3 — EXISTING BOOKING CREATION FLOW
1. **Frontend:** `frontend/assets/js/booking.js` creates payload and calls `/api/bookings` via `POST`.
2. **Backend:** `backend/controllers/bookingController.js` (`create`) receives payload.
3. **Database:** `backend/models/bookingModel.js` (`createManualBooking`) executes `INSERT`.
4. **Initial Data:** `status` = `"Pending"`, `payment_status` = `"Pending"`. No payment order ID is stored at creation.
5. **Redirection:** Returns new `booking.id`, frontend redirects to `payment.html?bookingId=<id>`.

## PART 4 — PAYMENT FLOW AUDIT
A. **Back navigation:** Booking remains `Pending` forever in DB.
B. **Browser refresh:** Reloads the payment page. Order may be re-created by Razorpay API.
C. **Razorpay modal close:** Booking remains `Pending` in DB.
D. **Payment cancellation:** Same as C.
E. **Payment failure:** Signature fails -> `paymentController.js` updates DB status to `"failed"`.
F. **Payment retry:** A user reopening the payment URL reuses the same DB booking ID.
G. **Successful payment:** Signature passes -> updates to `"Confirmed"`, `payment_status` to `"Paid"`.
H. **Reopening URL:** Safe. Reuses existing ID.

## PART 5 — EXISTING DATA SAFETY
The database already contains existing rows with `Pending` and `Confirmed`.
The safest fix MUST be backward-compatible with these existing records without modifying them in the database. 
Changing DB rows requires a migration script, carries data-loss risk, and might desync with manual records.

## PART 6 — STATUS FIX OPTIONS
**OPTION A (Safest): Frontend-only mapping update.** Modify `frontend/assets/js/pages/account.js` to accept `Pending` and `Confirmed` in `BK_TAB_STATUSES`.
- Risk: LOW. Zero database impact. Existing bookings become instantly visible.

**OPTION B: Backend normalization.** Modify `getUserBookings` to map `Pending -> payment-pending` and `Confirmed -> paid` before sending to frontend.
- Risk: LOW. Zero database impact.

**OPTION C: Database modification.** Update DB to use `payment-pending` and `paid` natively. 
- Risk: HIGH. Requires running `UPDATE bookings SET status = ...`.

*Recommendation:* **OPTION A** or **B**.

## PART 7 — ACCOUNT BOOKING DISPLAY
`account.js` maps statuses:
```javascript
const BK_TAB_STATUSES = {
  ongoing: ["payment-claimed", "paid"],
  pending: ["payment-pending", "failed"],
  completed: ["video-sent"]
};
```
If we adopt Option A, we simply change this to:
```javascript
const BK_TAB_STATUSES = {
  ongoing: ["payment-claimed", "paid", "Confirmed"],
  pending: ["payment-pending", "failed", "Pending"],
  completed: ["video-sent"]
};
```

## PART 8 — ADMIN BOOKING STATUS
`admin.js` handles status natively:
`const displayStatus = isVideoSent ? "Video Sent" : (b.status || "Confirmed");`
Admin works perfectly with `Pending` and `Confirmed`. A frontend-only change to `account.js` has ZERO impact on Admin.

## PART 9 — DUPLICATE BOOKING ROOT CAUSE
The frontend `booking.js` submits a POST to `/api/bookings` every time "Proceed to Payment" is clicked. The backend blindly executes `INSERT INTO bookings` without checking if an unpaid (`Pending`) booking for that exact Puja and User already exists.

## PART 10 — DEFINE "DUPLICATE BOOKING"
**Exact duplicate definition:** 
Same User Phone + Same Puja + Status is `"Pending"`.
If these match, the user is just re-attempting a session they abandoned earlier. 

## PART 11 — DUPLICATE PREVENTION OPTIONS
**OPTION A: Backend-only "Upsert/Find-first".** In `bookingController.js`, before calling `createManualBooking`, query the database for an existing `"Pending"` booking for this phone and puja. If found, return the *existing* booking ID instead of creating a new one.
- Risk: LOW. Completely eliminates duplicates without requiring DB schema changes or frontend changes.

**OPTION B: Frontend logic.** Try to store `bookingId` in `localStorage`.
- Risk: HIGH. Flaky across devices and incognito mode.

*Recommendation:* **OPTION A (Backend-only Find-first)**.

## PART 12 — PAYMENT RETRY SAFETY
Using Duplicate Prevention Option A guarantees payment retry safety. If the user creates a booking, abandons payment, and tries to book again later, the backend will return the *same* `bookingId`. The payment controller will then create a new Razorpay order for the *same* booking. 

## PART 13 — BACK/CANCEL BEHAVIOR
When navigating back or cancelling Razorpay, the booking remains `"Pending"`. This is the **correct business behavior**, acting as an "abandoned cart" that can be resumed. No changes should be made to cancellation logic.

## PART 14 — FAILED PAYMENT
Remains `"failed"`. No changes needed.

## PART 15 — SUCCESSFUL PAYMENT
Remains `"Confirmed"`. No changes needed.

## PART 16 — NOTIFICATIONS / SIDE EFFECTS
No automated notification side-effects depend on `"payment-pending"` or `"paid"`. Webhooks expect the current DB flow. Modifying only `account.js` is perfectly isolated.
